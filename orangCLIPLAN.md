# План разработки OrangeCTL на Go

## 1. Цель проекта

Создать универсальную CLI-программу `orangectl` для Orange Pi на языке Go.

Программа управляет десятью пользовательскими процессами через фиксированные слоты:

```text
slot1, slot2, slot3, slot4, slot5,
slot6, slot7, slot8, slot9, slot10
```

OrangeCTL не содержит заранее настроенных ботов, серверов или скриптов. Пользователь сам задаёт для каждого слота отображаемое имя, рабочую папку, команды запуска и остановки, лог, переменные окружения и другие параметры.

Главные преимущества реализации на Go:

- один исполняемый файл без Python и виртуального окружения;
- простая кросс-компиляция для `arm64` и `arm`;
- быстрый запуск и небольшое потребление памяти;
- стандартные средства Go для JSON, процессов, сигналов и тестирования.

## 2. Поддерживаемые команды

```bash
orangectl
orangectl menu
orangectl list
orangectl validate [slot]
orangectl start <slot>
orangectl stop <slot>
orangectl restart <slot>
orangectl status [slot]
orangectl logs <slot> [--lines 50] [--follow]
orangectl edit <slot>
orangectl reset <slot>
orangectl system
orangectl version
```

Без аргументов программа открывает интерактивное меню. Все команды должны иметь понятные коды завершения: `0` при успехе и ненулевой код при ошибке.

## 3. Технологический стек

- Go 1.23 или новее;
- `github.com/spf13/cobra` — команды, аргументы и флаги;
- `github.com/charmbracelet/lipgloss` — оформление терминального вывода;
- `github.com/charmbracelet/huh` — интерактивное меню и подтверждения;
- `github.com/shirou/gopsutil/v4` — системная информация;
- стандартная библиотека: `encoding/json`, `os`, `os/exec`, `syscall`, `context`, `path/filepath`, `bufio`, `time`, `log/slog`.

Не следует добавлять библиотеку, если задача надёжно решается стандартной библиотекой Go.

## 5. Конфигурация слота

Каждый файл `configs/slotN.json` имеет одинаковую схему:

```json
{
  "slot": "slot1",
  "enabled": false,
  "display_name": "Empty Slot 1",
  "description": "",
  "working_directory": "",
  "start_command": "",
  "stop_command": "",
  "restart_command": "",
  "log_file": "",
  "use_sudo": false,
  "auto_restart": false,
  "environment": {},
  "env_file": ""
}
```

Go-модель:

```go
type SlotConfig struct {
	Slot             string            `json:"slot"`
	Enabled          bool              `json:"enabled"`
	DisplayName      string            `json:"display_name"`
	Description      string            `json:"description"`
	WorkingDirectory string            `json:"working_directory"`
	StartCommand     string            `json:"start_command"`
	StopCommand      string            `json:"stop_command"`
	RestartCommand   string            `json:"restart_command"`
	LogFile          string            `json:"log_file"`
	UseSudo          bool              `json:"use_sudo"`
	AutoRestart      bool              `json:"auto_restart"`
	Environment      map[string]string `json:"environment"`
	EnvFile          string            `json:"env_file,omitempty"`
}
```

Декодер должен отклонять неизвестные поля через `json.Decoder.DisallowUnknownFields()`. Это помогает сразу находить опечатки в конфиге.

## 6. Пути и размещение данных

Пути по умолчанию должны соответствовать XDG:

```text
Конфиги:  $XDG_CONFIG_HOME/orangectl/ или ~/.config/orangectl/
Состояние: $XDG_STATE_HOME/orangectl/ или ~/.local/state/orangectl/
PID:       ~/.local/state/orangectl/pids/
Логи CLI:  ~/.local/state/orangectl/logs/
```

Для локальной разработки разрешить переопределение:

```bash
ORANGECTL_CONFIG_DIR=./configs
ORANGECTL_STATE_DIR=./state
```

При первом запуске `orangectl init` может создать десять пустых конфигов. Программа не должна перезаписывать существующие файлы без явного подтверждения.

## 7. Белый список слотов

В коде хранится фиксированный список:

```go
var AllowedSlots = []string{
	"slot1", "slot2", "slot3", "slot4", "slot5",
	"slot6", "slot7", "slot8", "slot9", "slot10",
}
```

Любой аргумент слота проверяется до построения пути. Значение `something`, `../slot1` или абсолютный путь должно быть отклонено. После проверки имя `slot4` однозначно соответствует `slot4.json`.

## 8. Валидация конфигурации

Команды:

```bash
orangectl validate
orangectl validate slot1
```

Проверки:

- слот входит в белый список;
- файл существует, является обычным файлом и содержит корректный JSON;
- неизвестные поля отсутствуют;
- поле `slot` совпадает с именем файла;
- обязательные строковые поля не состоят из пробелов;
- для включённого слота заданы `working_directory` и `start_command`;
- рабочая папка существует и является директорией;
- путь к логу не указывает на директорию;
- ключи переменных окружения корректны;
- `env_file`, если задан, существует и не выводится в терминал;
- конфигурация не пытается обойти границы через имя слота.

Вывод:

```text
SLOT    RESULT
slot1   OK
slot2   disabled
slot3   missing start_command
```

Ошибки должны быть обёрнуты через `%w`, чтобы вызывающий код мог применять `errors.Is` и `errors.As`.

## 9. Список и статус

`orangectl list` всегда показывает все десять слотов:

```text
SLOT    NAME          ENABLED  STATUS
slot1   Мой скрипт    yes      stopped
slot2   Empty Slot 2  no       disabled
```

`orangectl status slot1` показывает подробности одного слота, а `orangectl status` — краткий статус всех. Для автоматизации добавить глобальный флаг `--json`, при котором результат выводится как стабильный JSON без цветов и декоративных символов.

## 10. Запуск процесса

Алгоритм `orangectl start slot1`:

1. Проверить имя и загрузить конфиг.
2. Полностью провалидировать включённый слот.
3. Проверить PID-файл и убедиться, что процесс ещё не работает.
4. Создать лог-файл с безопасными правами доступа.
5. Сформировать окружение из `os.Environ()`, `env_file` и `environment`.
6. Создать `exec.Cmd` с указанной рабочей директорией.
7. Запустить процесс в отдельной группе процессов.
8. Перенаправить `stdout` и `stderr` в настроенный лог.
9. Сохранить PID и данные идентификации атомарной записью.
10. Проверить, что процесс не завершился сразу с ошибкой.

Строка `start_command` является shell-командой пользователя, поэтому на Linux её следует запускать явно через:

```go
exec.Command("/bin/sh", "-c", cfg.StartCommand)
```

Команду нельзя собирать конкатенацией из непроверенных CLI-аргументов. Значения окружения передаются через `Cmd.Env`, а не вставляются в командную строку.

## 11. PID-файлы и идентификация процесса

Одного PID недостаточно: Linux может повторно использовать номер завершившегося процесса. Файл состояния должен содержать JSON:

```json
{
  "slot": "slot1",
  "pid": 1842,
  "started_at": "2026-08-01T10:30:00Z",
  "proc_start_ticks": 123456,
  "working_directory": "/home/user/project"
}
```

Перед `status`, `stop` и `restart` проверить:

- процесс `/proc/<pid>` существует;
- время старта процесса совпадает с сохранённым;
- рабочая папка и ожидаемая команда согласуются с конфигом;
- PID-файл принадлежит текущему пользователю и не является симлинком.

Устаревший PID-файл удаляется только после этих проверок. Запись PID-файла выполняется во временный файл с последующим `os.Rename`.

## 12. Остановка и перезапуск

Если задан `stop_command`, программа выполняет его и затем проверяет завершение процесса. Иначе:

1. Проверяет принадлежность PID слоту.
2. Посылает `SIGTERM` группе процессов.
3. Ждёт до настраиваемого тайм-аута, по умолчанию 10 секунд.
4. Если процесс не завершился, возвращает ошибку и предлагает `--force`.
5. Только с `--force` посылает `SIGKILL`.
6. После подтверждённой остановки удаляет PID-файл.

`restart` использует `restart_command`, если он задан. Иначе выполняет безопасную последовательность `stop → подтверждение остановки → start`.

## 13. Логи

```bash
orangectl logs slot1
orangectl logs slot1 --lines 100
orangectl logs slot1 --follow
```

По умолчанию выводятся последние 50 строк. Реализация не должна загружать большой файл целиком в память: чтение последних строк выполняется блоками с конца файла. Режим `--follow` продолжает чтение до `Ctrl+C`, используя `context.Context` и обработку сигналов.

Читать можно только файл, явно заданный в `log_file`. Содержимое `env_file` и значения переменных окружения никогда не печатаются.

## 14. Редактирование и сброс

`orangectl edit slot1` открывает строго соответствующий JSON-файл. Редактор выбирается в порядке:

1. `$VISUAL`;
2. `$EDITOR`;
3. `nano`.

После закрытия редактора конфиг автоматически валидируется.

`orangectl reset slot1`:

- требует интерактивного подтверждения либо флага `--yes`;
- не сбрасывает работающий слот без его остановки;
- создаёт резервную копию в `configs/backups/`;
- атомарно записывает пустой шаблон нужного слота.

## 15. Использование sudo

По умолчанию `use_sudo` равен `false`. Если поле включено, CLI предупреждает пользователя и вызывает `sudo` только для команды конкретного слота. Сам `orangectl` не должен постоянно работать от root.

Для надёжной эксплуатации предпочтительнее отдельный unit systemd с минимальными разрешениями, чем произвольный запуск всего CLI через `sudo`.

## 16. Интерактивное меню

Команды `orangectl` и `orangectl menu` открывают меню:

```text
ORANGECTL
1. Список слотов
2. Запустить слот
3. Остановить слот
4. Перезапустить слот
5. Статус
6. Логи
7. Редактировать конфиг
8. Проверить конфиги
9. Информация о системе
0. Выход
```

Для запуска показываются только включённые и валидные слоты. Для редактирования — все десять. Цвет отключается автоматически, если вывод не направлен в TTY, и вручную через `NO_COLOR` или `--no-color`.

## 17. Системная информация

`orangectl system` показывает:

- hostname и uptime;
- загрузку CPU;
- использование RAM и диска;
- модель платы, ОС и ядро;
- локальные IP-адреса;
- температуру CPU, если доступен `/sys/class/thermal/thermal_zone*/temp`.

Отсутствие датчика температуры не считается фатальной ошибкой: выводится `unavailable`. Команда не должна зависеть от конкретной модели Orange Pi.

## 18. Сборка и установка

Инициализация модуля:

```bash
go mod init github.com/USER/orangectl
go mod tidy
```

Локальная сборка:

```bash
go build -trimpath -ldflags="-s -w" -o bin/orangectl ./cmd/orangectl
```

Кросс-компиляция для 64-битной Orange Pi:

```bash
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build \
  -trimpath -ldflags="-s -w" \
  -o dist/orangectl-linux-arm64 ./cmd/orangectl
```

Для 32-битной системы:

```bash
GOOS=linux GOARCH=arm GOARM=7 CGO_ENABLED=0 go build \
  -trimpath -ldflags="-s -w" \
  -o dist/orangectl-linux-armv7 ./cmd/orangectl
```

Установка на Orange Pi:

```bash
sudo install -m 0755 orangectl-linux-arm64 /usr/local/bin/orangectl
orangectl version
orangectl init
```

Версия, commit и дата сборки внедряются через `-ldflags -X`.

## 19. Тестирование и качество

Обязательные команды проверки:

```bash
go fmt ./...
go vet ./...
go test ./...
go test -race ./...
```

Тесты должны покрывать:

- загрузку корректного и повреждённого JSON;
- отклонение неизвестных полей;
- все правила валидации;
- защиту имени слота от path traversal;
- устаревший и переиспользованный PID;
- запуск, остановку и перезапуск временного процесса;
- чтение последних строк и отмену `--follow`;
- атомарную запись состояния;
- JSON-вывод команд.

Для файловых тестов использовать `t.TempDir()`, для времени и `/proc` — небольшие интерфейсы с тестовыми реализациями. Интеграционные Linux-тесты отделить build tag `integration`.

## 20. Этапы разработки

### Этап 1 — Go-каркас и конфиги

- создать `go.mod`, `cmd/orangectl` и пакеты `internal`;
- реализовать `init`, `list` и `validate`;
- добавить десять пустых JSON-конфигов;
- добавить базовые unit-тесты.

### Этап 2 — управление процессами

- реализовать `start`, `status`, `stop`, `restart`;
- добавить группы процессов, тайм-ауты и корректную обработку сигналов;
- безопасно хранить PID и идентификатор времени старта.

### Этап 3 — логи и конфиги

- реализовать `logs`, `--lines`, `--follow`;
- добавить `edit` и `reset` с резервной копией;
- реализовать `environment` и `env_file` без раскрытия секретов.

### Этап 4 — интерфейс и системная информация

- добавить интерактивное меню;
- реализовать `system`;
- добавить `--json`, `--no-color` и единый формат ошибок.

### Этап 5 — релиз для Orange Pi

- подготовить `Makefile` и скрипт установки;
- собрать `linux/arm64` и `linux/armv7`;
- проверить бинарники на реальном устройстве;
- оформить README, changelog и контрольные суммы релиза.

### Этап 6 — дополнительная интеграция systemd

- подготовить шаблон `orangectl@.service`;
- документировать автозапуск и перезапуск;
- оставить systemd опциональным, чтобы базовые команды работали без него.

## 21. Критерии готовности

Версия 1.0 готова, когда:

- один бинарник работает на поддерживаемых Orange Pi без внешнего runtime;
- все десять пустых слотов создаются и валидируются;
- полный цикл `start/status/logs/restart/stop` работает предсказуемо;
- CLI не завершает чужой процесс при устаревшем PID;
- конфиги и состояние записываются атомарно;
- секреты не попадают в вывод и логи CLI;
- команды пригодны и для человека, и для скриптов через `--json`;
- unit- и интеграционные тесты проходят на Linux ARM;
- установка и удаление описаны в README.

## 22. Ограничения проекта

В репозиторий нельзя добавлять реальные пользовательские проекты, токены, API-ключи, `.env`, домашние пути или заранее заполненные команды. Все слоты поставляются выключенными и пустыми.

Главный принцип остаётся неизменным:

> OrangeCTL ничего не знает о конкретных программах пользователя. Он безопасно управляет десятью универсальными слотами, описанными конфигурационными файлами.
